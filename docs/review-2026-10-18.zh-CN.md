## 1. 复查方法（为什么这几条能查出来）

1. **不读注释、只读调用链**。这个仓库的注释极其详尽，但注释描述的是"当时的意图"。
   本次 11 条里有 4 条正是"注释写着有这个行为、代码里根本没有"：
   `_in_rem_comment` 的 docstring 说"字符串里的 rem 不算"（代码照算）、
   `delete_pair_here` 的 docstring 说"落光标单独 try"（代码没 try）、
   `v100 补括号` 的整段（读的键后端从不返回）、
   `source()` 的 docstring 说"按开关语义"（被第二份定义覆盖）。
   → 结论：**docstring 只能当线索，判据必须回到"这个变量到底是谁赋的值"**。
2. **往上追一层"生产者"**。`ctx["word_start_col"]` 这类键不看使用处、只看生产处
   （`VbeBackend.get_context()` 的 return）就能一眼看死。
3. **用探针实测数值，不靠推理**。掩码行数、`proc_at_line` 归属、
   `_caret_char_col` 的换算结果，全部用一次性脚本跑出真值再写断言
   （MEMORY 第 22/24 条）。
4. **A/B 是唯一的照妖镜**。每条修复后都把旧实现临时打回去跑一遍，
   确认对应用例由绿变红（见 §5.2）。第一版 110.2 我写的断言**旧实现也通过**
   —— 因为 `proc_at_line` 压根不做续行合并，是我把判据放错了层；
   换成 `extract_records` 才真正区分开。
5. **遵守 §90 护栏**。第 110 节所有猴补丁（`_get_vbe_cached` / `_sem_cache` /
   环境变量 / `engine` 模块常量）都在 `finally` 里还原，跑完 90.1 仍然是空的。

### 2.1 ★★★ v100「给 VBE 补进来的过程名补括号」从来没执行过（死代码）

- **位置**：`engine.py:2223`（`Completer.trigger` 里 `if not self._accept_pinned:` 分支）
- **症状**：用户接受 Tab 补全后，VBE 自己把过程名塞进了行里；我们本该在它后面补
  `()`。实际什么都没发生 —— 用户以为"这个功能没做"，其实代码写了整整 20 行。
- **根因**：那一段从 `ctx` 取 `word` / `word_start_col` / `word_end_col`，
  而真实后端 `VbeBackend.get_context()` 的 return **没有这三个键**
  （它只给 `line_no / caret_col / line_text / decl_* / member_root_name`）。
  于是 `_ws100` 恒 0、`_word100` 恒空串，守卫
  `if _word100 and _ws100 > 0 and _we100 >= _ws100` 永远不成立。
- **为什么 1131 条用例全绿**：测试里的假后端**自己塞了这三个键**（假工程比真后端"更完整"）。
  这是本仓库最危险的一类假绿：**用例在测一个不存在的契约**。
- **顺带修掉的两个隐患**：
  - `_type_list_anchor` 有一行不可达的 `return j + 2`（`j` 未定义，ruff F821）。
  - `except` 分支的日志引用 `_word100` —— 若第一行 `int(start_col)` 就抛，
    它还没绑定 ⇒ `NameError` 会把外层的 hide / 记账逻辑一起带走。
    改为引用 try 之前就初始化好的 `_word_init`。
- **修法**：直接用 `trigger` 前面已经算好的 `word / start_col`（与 `accept()`
  同一份 `extract_word_at` 结果，字符列口径一致）。
- **钉桩**：§72.1c（新）—— 第 1 轮补全命中后行尾必须是 `getTitle()`；
  §79.2.8 断言反转（旧护栏 `'ctx.get("word_start_col")' in 源码` **保护的正是这个 bug**）。

### 2.3 ★★★ 未闭合的引号会把整份掩码压成一行 → 过程归属错乱

- **位置**：`parser.py:224`（`_mask_strings_and_comments`）
- **症状**：用户刚敲下 `s = "abc`（右引号还没打），此后**所有**与"这段代码属于哪个过程"
  有关的判断全部错位：别的函数里的局部变量冒出来、声明区的变量消失。
- **根因**：一整段连续的被掩码字符（**含换行**）被压成一个空格 ⇒ 掩码后的行数比原文少。
  A/B 实测两种中间态：
  - 引号**一直不闭合**（刚敲下 `s = "abc`）：7 行变 **3 行**，`Sub B()` 的头被抹掉，
    B 里的 `Dim y` 被算成 A 的；
  - 引号**在后面某行闭合**：9 行变 **7 行**，`proc_at_line(code, 7)` 从 `"B"` 变 **None**
    （第 7 行 `Dim z As Long` 直接不知道自己属于谁）。
- **修法**：按行各留一个空格、换行一个不少（行数严格不变），
  并在 docstring 里写明"本函数产物长度仍不等长，按下标对齐请用 `scan_code_states`"。
- **钉桩**：§110.3（行数相等 + `proc_at_line(code,7) == "B"`，A/B 实测旧实现给 `None`）。

### 2.4 ★★★ `Rem` 不参与掩码 + `_in_rem_comment` 误判字符串

- **位置**：`parser.py:137`（`scan_code_kinds`）、`parser.py:208`（Rem 分支）、
  `engine.py:452`（`_in_rem_comment`）
- **症状**（三组，都是真的会遇到）：
  1. `Rem 说明 _` 的行尾 `_` 被 `_RE_CONTINUATION` 当成续行 ⇒ 下一行（常常是
     `End Sub`）被并进注释 ⇒ 过程作用域一直不结束 ⇒ 后面整段**模块级**代码
     被算成该过程的局部变量。实测：`Dim m As Long` 的 `proc` 从 `None` 变成 `"A"`。
  2. `Rem Dim count As Long` 解析出**幻影记录** `Rem`（A/B 实测旧实现 records 多出 `Rem`）。
  3. `_in_rem_comment` 自己用 `find("rem")` ⇒ `x = "the rem value"` 里那一格被当成
     Rem 注释 ⇒ 成员位置判定被误杀、`c.` 该让位给 VBE 成员列表的地方**不让位**。
- **根因**：同一个语法（哪一格是注释）被两条路径各实现一份，其中一份漏了 Rem
  （MEMORY 第 14 条的重演）。
- **修法**：把"这一格是字符串 / `'` 注释 / Rem 注释"下沉成**唯一实现**
  `parser.scan_code_kinds()`（位掩码 `KIND_STRING/KIND_COMMENT/KIND_REM`），
  `scan_code_states()` 退化成它的 bool 视图，`_in_rem_comment` 只取 `KIND_REM` 那一位。
  Rem 的语法规则（整词 + 前面是行首 / `:`）写在扫描器里，因为它**逐字符扫过整份代码、
  往回跳过空白就能判断** —— 当年"状态机看不到行首"的理由并不成立。
- **钉桩**：§110.1 / §110.2 / §110.4 / §110.5。

### 2.5 ★★★ "文本已写进去、落光标失败"却返回 False —— 6 处

- **位置**：`vbe_bridge.py:4863`（`insert_pair`）、`:4989`（`_wrap_selection`）、
  `:5058`（`insert_snippet`）、`:5971`（`new_line_below`）、`:6244`（`new_line_above`）、
  `:6463`（`delete_pair_here`）
- **症状**（用户可见，都是"多出东西"）：
  - 敲 `(` 得到 `( (`（文本已写，返回 False ⇒ 调用方把按键还给系统）；
  - 敲 `(` 包裹选区后多出一个 `(`；
  - 片段插入提示"失败"，用户再点一次 ⇒ 插两遍；
  - 回车多出一行（新行已插，落光标抛异常 ⇒ 调用方再注入一个回车）；
  - 删一对括号变成多删一个字符。
- **根因**：`SetSelection` / `_resolve_sem_info`（要探测列语义）与"写文本"
  在同一个 `try` 里，异常直接 `return False`。而"返回 False"在调用方的语义是
  **"我没管，你把按键还给系统"** ⇒ 补偿式重复输入。
- **修法**：文本写成之后的落光标动作一律单独 `try`，失败只记日志、按成功返回。
  `duplicate_lines` / `delete_lines_here` 早就是这个口径，这次把剩下 6 处拉齐。
- **钉桩**：§110.8（假 COM 的 `SetSelection` 抛异常，`insert_pair` 仍须返回 True
  且行里已有 `()`）。

### 2.6 ★★ `insert_snippet` 的终点列把显示列当字符下标

- **位置**：`vbe_bridge.py:5121`
- **症状**：单行选区 + 含全角 / Tab 的行，插入片段会**丢掉用户代码**。
  实测：`s = "中文"` 在 `中` 与 `文` 之间插 `X`，得到 `s = "中X"` —— `文` 没了。
- **根因**：`el == sl` 那支直接 `col_e = ec`（VBE 的 `ec` 是**显示列**），
  而 `tail = last[j:]` 之后是**整行重写**，多减一格就是真的删字。
- **顺带**：`max(i, …)` 只对单行有意义 —— 多行选区时 `i` 是**首行**下标，
  却拿去给末行的 `j` 兜底（从某行中部往下选到下一行行首，末行未选中部分被整段丢弃）。
- **修法**：两端口径统一换算（同一组 `sem/tabw/wide2`）；`max(i, …)` 只留在单行分支。
- **钉桩**：§110.10（`s = "中X文"`，A/B 实测旧公式得到 `s = "中X"`）。

### 2.7 ★★ `enter_indent_wanted` 的"光标在行尾"判据差一格

- **位置**：`vbe_bridge.py:1296`
- **症状**：块头行（如 `    For i = 1 To 10`）上，光标停在**最后一个字符之前**

  （行内已排除 Tab；纯 ASCII 时 `_eol_disp_col` 就是 `len+1`）。
  "行尾"这个语义只留一份算法，与 v93 用的是同一个函数（MEMORY 第 21 条）。
- **钉桩**：§110.11（19 → 放行、20 → 接管、21 → 放行）。
  注：既有 §56.6 / §73.5b 的数据本来就是正确的行尾列（20），收紧后照旧通过。

### 2.13 ★★★ `insert_snippet` 多行插入非原子（第二轮）

- **位置**：`vbe_bridge.py` `insert_snippet` 的写入段
- **症状**：插入多行片段时第 2 行起逐行 `InsertLines`，**只要有一行抛异常**：
  已经写进去的前几行留在文档里，函数却返回 False ⇒ 调用方提示"插入失败"，
  用户再点一次 = **片段插两遍**。首行更是先被 `ReplaceLine` 改掉，
  失败时用户的半行代码直接没了（实测 `x = ab` 变成 `x = a`）。
- **修法**：写入顺序改成"**先一次插中间行、再覆盖首行**"，并补两条回滚：

".join(...))` —— 一次 COM 调用要么全成
    要么全不成；
  - 中间行失败 → 原文一个字都没动（若为"虚拟空行"场景，把刚建的空行删掉）；
  - 首行覆盖失败 → 只删**新增的**行（`_virtual` 时连那个空行一起删），
    回到"什么都没发生"。⚠️ 第一版回滚写成"从 sl 起删 k+1 行"，会把用户

  - 多行选区的旧行删除失败只记日志、仍返回 True（片段内容已经在文档里，
    报失败会让用户再插一遍）。
  - 光标在"模块末尾虚拟空行"上的情形单独处理：先把那一行建成真实空行。
- **钉桩**：§111.4（一次调用）、§111.5（插不进去时首行不变）、
  §111.6（首行写不进去时回滚且不删原有行）、§111.7（虚拟空行 + 多行片段）。

### 2.14 ★★ `duplicate_lines` 与 `insert_snippet` 对 `InsertLines` 的假设互相矛盾（第二轮）

- **症状**：两处对**同一个 API** 的假设完全相反 —— `duplicate_lines` 说
  "`cm.Lines()` 的原文直接喂回去，VBE 会按换行拆开"，`insert_snippet` 说
  "VBE 怎么拆行没有文档保证，必须逐行插"。至少有一处是错的；而"哪一处错"
  决定了另一个功能是否一直在踩雷。
- **裁决（真机实测，Excel 2016 / VBE7.1）**：`InsertLines` 对 **`\r\n`、`\n`、
  `\r` 三种换行都正确拆行** ——
  3 行文本插进去就是 3 行；只有"文本自身以换行结尾"时多出一个空行（那正是
  要插的空行）。`cm.Lines(n, count)` 的 join **不带**尾随换行，所以原样回灌
  不会多出空行。
- **结论**：`duplicate_lines` 的假设是对的，`insert_snippet` 的谨慎是多余的。
  两处现在统一成"整段一次 `InsertLines`"（见 §2.13），注释里写明实测依据。
- **钉桩**：§111.8（`Ctrl+D` 复制整行仍然只用一次 `InsertLines`）。
- **顺带修**：测试里的假 `CodeModule.InsertLines` 原来只按 `\n` 拆，
  现在按真机行为拆三种换行（§99.4 的假对象已同步）—— 假对象比真对象"更弱"
  同样是假绿的来源。
